## 5. 根因

### 5.1 为什么“只有收藏能播”

1. 收藏条目解析出的档位集合只有 standard，取流只请求 1 档，拿到完整 MP3（L84-L126）。
2. 搜索/歌手/榜单/首页条目带上游 `fileInfos` 档位，`audioFiles` 先请求 7/5/3，`qualityType=5` 返回 Hi-Res FLAC（L134-L135、L183-L184）。
3. `chooseQuality` 默认 `hiRes`，选中 FLAC（L140、L157、L189）。
4. iOS AVPlayer 对这类 FLAC `setSourceUrl` 失败（L144、L161、L193）。
5. 旧 `MuyuAudioController.playSong` 只 `firstWhere` 选一个文件并 `play` 一次；异常只写 `error`，不会用同一响应里的 lossless/standard 再试。

所以不是“收藏对象有 URL”，而是“收藏刚好只有 MP3 档；其他入口有 Hi-Res 档，而播放器又不能播这个 FLAC，且失败后不降档”。

> 未找到：AVPlayer 拒绝该 FLAC 的精确底层原因（MIME、容器、位深/采样率或代理 Range 组合）。本轮采用“标准 MIME + 播放失败逐档降级”双重兜底，不依赖单点猜测。

### 5.2 为什么显示“独立板块未返回歌曲”

本日志能确认三点：

1. **8011 真空**：L61 `featuredSongs raw=0 parsed=0 empty=true`（20:04:09.490），不是 990000。
2. **`privatefm` 请求体类型错误**：L56 服务端明文报 `Cannot deserialize value of type java.lang.String from Array value`；旧代码把 `refInfo` 传成 `[]`（修复前 `lib/protocol/huawei_api.dart` `privateFm`）。这会让“现在就听”的独立接口稳定 400。
3. **`recommend/playlist` 稳定 400 0B**：L58-L59，响应没有 body，具体字段**未找到**。

代码层还有两个会把“有数据”变成“空列表”的路径：

4. `parseDiscover` 只在 `remaining`（未带 heart/new/hot/recommend 标签的 pmf001 批次）非空时给 `listen/recommended/heart/new/hot` 分槽。真实首页若 pmf001 的批次全部带标签，`remaining` 为空，`listen` 和 `recommended` 就保持空。
5. `discover()` 之后又调用 `_dedupeHomeSections`，用一个全局 `seen` 按 daily→listen→recommended→hot→heart→new 去重。推荐/电台的歌曲如果和 24926 热歌重复，会被整段删掉，最终变成空列表；UI 就显示“独立板块未返回歌曲（不回填其他列表）”。

另外，旧 `parseSong` 在完全缺 ID 时生成时间戳假 ID；这类条目能显示、能点，但 `bycontentcode` 必然失败。本日志的播放行都有真实 ID，**未找到**假 ID 实例，但这是确定的代码风险。
